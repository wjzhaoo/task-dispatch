## 1. 背景与目标

- 为什么做：当前安装器支持 `qoderwork`，但不支持 Qoder IDE/CLI 官方使用的用户级 Skill 目录。
- 官方现状：Qoder CLI 文档声明用户级 Skill 位于 `~/.qoder/skills/{skill-name}/SKILL.md`，项目级 Skill 位于 `.qoder/skills/{skill-name}/SKILL.md`。
- 完成后的可观察效果：执行 `node scripts/install.js qoder`，可将完整的 `task-dispatch` Skill 安装到指定用户目录下的 `.qoder/skills/task-dispatch/`；`all` 自动包含 Qoder；帮助、README 和测试与实际行为一致。
- 本阶段边界：仅增加 Skill 安装/发现支持。Qoder 暂按无原生唤醒平台处理，继续使用 task-dispatch 的通用 `wait/resume` 协作方式，不虚构已有 Qoder 会话注入协议。

## 3. 方案与关键决策

### 方案 A：安装器级支持（推荐）

- 思路：新增 `qoder -> .qoder/skills` 平台映射；安装前验证 Qoder 所需的 YAML frontmatter；补充专门测试和 README 说明。
- 影响面：`scripts/install.js`、`scripts/verify.js`、`README.md`。
- 风险：低。沿用现有复制安装、预检、冲突保护、收据和 `all` 语义。
- 推荐理由：与 Qoder 官方公开契约直接对应，能形成可验证的最小闭环，不引入无法实机证明的私有唤醒协议。

### 方案 B：安装器支持 + 原会话主动唤醒

- 思路：在方案 A 基础上新增 Qoder wake adapter、会话发现、续接选择、CLI 参数、测试和接入文档。
- 影响面：安装器、多个 `runtime/adapters`/`runtime/core` 文件、客户端、测试与文档。
- 风险：高。当前没有已确认的 Qoder 本地会话发现文件、认证方式、状态读取和消息注入协议；无法满足“不得猜测”的项目规则。
- 采用条件：用户提供可复现的 Qoder 本地 API/SDK 契约或允许基于真实 Qoder 环境另开调研任务。

### 推荐方案的端到端流程

```mermaid
flowchart LR
    A[用户执行 install.js qoder] --> B[校验平台名与 YAML frontmatter]
    B --> C[预检目标路径和本地冲突]
    C --> D[复制 Skill 到 .qoder/skills/task-dispatch]
    D --> E[写入安装收据]
    E --> F[Qoder 新会话或 /skills reload 后发现 Skill]
    F --> G[task-dispatch 使用通用 wait/resume 协作]
```

### 决策记录

- 推荐方案 A；本阶段不修改唤醒运行时。
- 保留 `qoderwork`，不把它重命名为 `qoder`，避免破坏现有用户。
- 不修改 `VERSION`、`package.json`、插件清单或 `CHANGELOG.md`：当前仓库的版本源已存在 `0.5.1` 与 `0.4.3` 不一致，属于任务开始前的既有状态，未经授权不顺带修复。
