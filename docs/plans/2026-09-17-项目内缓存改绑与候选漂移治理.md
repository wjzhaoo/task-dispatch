## 3. 方案与关键决策

### 3.1 推荐方案

```text
系统级索引/安全元数据
        │ workspace → dataRoot
        ▼
D:\test\.task-dispatch\runtime\<project-key>\
        ├─ state / receipts / artifacts / reviews
        └─ 单项目 service.lock + endpoint

管理台选择绑定 → 创建一次性改绑邀请 → 新会话确认真实平台并接入
       → 服务原子替换 binding / 撤销旧 token / 更新 attempt 所有权
       → 邀请完成或回滚，管理台显示结果

worker 候选 → 比较实时工作区
       ├─ 仅 authority/control 文件漂移：审计记录后继续候选审核
       └─ 任一业务文件漂移：保持阻塞，要求显式协调
```

- 数据目录：取消新项目的旁挂目录与空公共服务默认启动；项目重数据写入 `.task-dispatch/runtime/<project-key>/`，并从快照、Git 建议和业务候选中排除 `runtime/`。
- 系统索引：保留一个小型注册表，记录项目工作区、数据根、最后发现时间和服务状态；不再创建用户级公共项目服务目录。
- 凭据：用户选择严格项目内方案。凭据进入 `.task-dispatch/runtime/<project-key>/clients/`，通过局部 ignore、快照强制排除、私有目录权限和敏感文件 0600 写入降低泄漏风险。
- 改绑：复用现有邀请/恢复逻辑，新增服务端一次性 rebind invitation 状态机与管理台入口；不采用“先强制解绑再连接”的非原子窗口。
- 关联状态：成功改绑时一次事务内更新 binding、wake/session、未结算 attempt 的合法所有权、pending handover、connection descriptor 和旧 token 撤销；失败保持旧绑定或明确停在 pending，不出现双重所有者。
- 候选漂移：不扩大大脑对业务实现的权限。新增“控制面漂移分类”，仅允许 `plan/contract/status/review/closeout` 等已受保护 authority files 在候选生成后变化；业务文件仍须与候选完全一致。
- 审核恢复：对纯控制面漂移提供“刷新并继续审核”或自动安全续审；不把审核阻塞转换成 worker 执行重试。`restartWorker=true` 继续受 repair authorization 保护。

### 3.2 备选方案

- 方案 B（最小改动）：仅把旁挂目录改成项目内目录，管理台执行“解绑后生成普通邀请”，并把 `.task-dispatch/plan.md` 加入快照排除。改动小，但改绑存在空窗，且完全排除计划文件会失去 worker 越权检测，不推荐。
- 方案 C（严格全项目内）：索引之外连凭据也放 `.task-dispatch/private/`。目录最集中，但仓库误提交、共享盘读取和备份泄密风险更高，需要额外 ACL、ignore 与安全检测。
