1. 两项目的 bindings 均无 wake 配置，各审核尝试没有 wakeNotice。已完成轮的大脑两次通过 wait 收到终审，MiMo/CodeArts 也通过 wait 领取，未发生本服务的通知唤醒。
2. MiMo：T01 submit 后实际调用 wait，拿到 T02；T02 submit 后再次 wait，返回 completed:true 后输出结束报告。因此“直接结束而没有等待”不符合这轮日志。
3. CodeArts：T01/T02 submit 后都有实际 wait。00:39 左右的等待被宿主 120 秒上限终止，下一次报已有等待锁；00:43 左右的等待被 110 秒上限终止，又出现锁冲突。最终一轮 wait 收到 completed:true 后正常退出。
4. 旧项目的 Codex worker 也记录了活跃 node PID 对应的 wait 锁冲突；旧 worker/reviewer 回合状态为 interrupted。无法仅凭这条记录断言是模型主动结束，也不应自动删除活跃锁。
5. “所有端接入后，由用户再次通知大脑开始”应保留。接入阶段报告就绪与测试开始后持续协作是不同阶段，不能把接入就绪回复当作整轮任务完成。

## 已在源码中修正

- 快速模板改为两阶段手动操作，禁止自动派生及发令前 plan；支持唤醒的平台须实际配置 wake-bind/park，并逐端记录完整唤醒证据。
- 明确核对宿主真实目录、服务 workspace 与邀请路径一致；无唤醒平台在用户启动后每次提交实际 wait，单次时长短于工具超时。
- submit 返回明确的 nextAction/nextInstruction，区分 park、wait、阶段 claim、attention 和项目结束；重复提交同样返回后续动作。
- status.connections 公开不含令牌的会话/唤醒配置及 armed 状态，方便大脑检查三端准备情况。armed 不是已成功唤醒的证明。
- 核对代码时另发现 MiMo 初始 SSE 状态可能 unknown：原小脑在线探测会把它当成不能续约，导致可访问的小脑过 120 秒后被跳过。现以成功查询当前会话列表与历史作为可达证据续约，同时仍校验会话 ID 和项目目录，不把 unknown 推断为空闲。此问题是代码检查发现，不是本轮日志中已经发生的故障。
