# 任务总结 — 各端连接耗时

## 根因

通用唤醒连接流程重复读取同一宿主会话；MiMo 的完整读取还会等事件流最多 800 ms，因此有可消除的额外开销。本地服务状态和目录索引测量仅约 1–10 ms。

最近试跑另有直接证据：最后的 `zcode` 执行端 12:17:38 已绑定，续接配置耗时 3 ms；大脑 12:27:16 才发出 `start-work`，12:35:32 登记第一项任务。该任务因 `bin/convert/PrusaSlicer.dll` 超过 32 MiB 单文件快照上限而进入关注，12:37:58 重试后于 12:38:00 产生首个执行尝试；现有快照配置已排除 `bin/`。`zcode` 为等待型端，没有使用本次优化的宿主核实代码。两次命令之间的模型或人工用时无法由服务日志进一步拆分。

## 修复

内部连接流程复用已核实的宿主结果；直接 `wake-bind` 仍自行核实。MiMo 首次连接只核实会话身份和模型，不采样事件状态；监控与唤醒读取继续采样。

## 验证与限制

单次唤醒型连接的宿主核实调用次数由两次降为一次；MiMo 连接核实不请求事件流。`npm test` 261/261 通过。这项优化不能缩短最近 `zcode` 端等待 `start-work` 和任务登记的时间；此前将它概括为最近慢连接的根因并不准确。
