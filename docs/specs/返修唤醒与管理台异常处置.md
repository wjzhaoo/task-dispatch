# 返修唤醒与管理台异常处置 — 技术方案

## 1. 需求概述

- **功能目标**：修复审核退回后 worker attempt 已创建但会话未领取导致的停滞；为异常任务提供可审计的恢复操作；调整管理台拓扑与操作入口。
- **验收标准**：未领取通知只自动补提醒一次，继续未领取则告警；管理员可对合法状态再次提醒、重试、追加额度或改派；初审端位于大脑与调度服务之间。
- **需求来源/提出人**：用户当前请求。

## 2. 影响面分析

| 涉及项 | 类型（模块/文件/接口） | 影响说明 |
|--------|------------------------|----------|
| Wake 状态机 | `runtime/core/wake.cjs` | 追踪 sent-but-unclaimed 宽限期、补提醒与停滞状态 |
| 监控快照 | `runtime/core/monitor.cjs` | 输出未领取停滞告警 |
| 管理命令 | `runtime/admin.cjs` | 增加显式再次提醒并保护 attempt/binding 状态 |
| Web 管理台 | `runtime/web/*` | 主页快捷操作、异常任务操作、四段式角色拓扑 |
| 回归测试 | `tests/wake.test.cjs`、`tests/pre-review.test.cjs`、`tests/admin.test.cjs` | 覆盖自动与人工恢复边界 |

## 3. 边界与异常场景

| 场景 | 预期行为 |
|------|----------|
| 首次通知 sent，宽限期内未 claim | 不重复发送 |
| 宽限期结束仍未 claim | 发送一次使用独立 marker 的补提醒 |
| 补提醒后仍未 claim | 标记 stalled 并在管理台告警，不再自动发送 |
| 投递结果 uncertain | 不自动重发，要求人工核实 |
| attempt 已领取、结算、替换或项目暂停 | 自动/人工提醒均拒绝或跳过 |
| 管理操作使用旧 revision/attemptId | 服务拒绝陈旧操作 |
| 宿主读取或发送永久不返回 | 读取 15 秒、发送 30 秒后释放 wake runner；读取后续可重试，发送按 uncertain 处理 |

## 4. 技术方案

- **选定方案**：方案 B，受控自动补提醒 + 异常告警 + 人工恢复。
- **被否决方案**：仅人工重试会继续静默停滞；把送达视为领取会伪造执行事实。

### 关键设计

- `wakeNotice` 保留首次发送证据，并增加领取宽限、补提醒次数/marker、停滞与人工请求字段。
- 自动补提醒使用不同于首次通知的 marker，发送前再次读取当前项目、binding 与 attempt，保证只作用于同一未领取 attempt。
- 人工再次提醒只创建持久化请求，由 wake 循环在目标会话空闲且状态仍合法时执行；不直接绕过投递保护。
- 所有宿主适配器调用由共享超时层包裹，防止单个悬挂 Promise 永久占用 `Wake.busy` 或监控 probe 的 `inFlight`。
- 主页快捷按钮复用现有 commandId、revision、确认和命令收据机制，不另建旁路 API。

## 5. 实现流程（必填章节）

1. 审核返回 `needs_fix`，调度器创建新的 worker attempt。
2. wake 首次发送任务通知并记录 marker/时间。
3. 宽限期后仍未 `claimedBy`，发送一次补提醒并记录独立 marker。
4. 再次超时后输出 `claim_stalled` 告警，停止自动补发。
5. 管理员可在主页对当前异常 attempt 执行再次提醒或其他适用恢复操作。
6. 宿主调用超时会释放本轮 runner 并记录可见错误，不阻塞后续 tick。
7. attempt claim 后清除 binding 的 armed 状态；旧提醒请求因 attempt/claimed 状态失效。
