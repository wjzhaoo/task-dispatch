# 项目内缓存改绑与候选漂移治理 — 技术方案

> 本文为历史方案记录。旧目录发现、迁移、旧页面与旧接入命令已移除；当前行为和接入步骤以 [运行文档](../runtime.md) 为准，完整现行数据继续使用，不自动补齐或迁移。

## 1. 需求概述

- **功能目标**：将服务数据与凭据严格收敛到项目内 `.task-dispatch/`；系统缓存仅保留项目目录索引；管理台生成一次性改绑提示词并原子更新关联状态；仅控制面文件漂移时允许继续候选审核。
- **验收标准**：新项目不再创建用户级公共服务目录；单项目只运行一个项目服务；改绑无双所有者与无永久 pending；`.task-dispatch/plan.md` 更新不阻塞审核，业务文件漂移仍阻塞。
- **需求来源/提出人**：用户确认采用严格项目内凭据方案并要求开始实施。

## 2. 影响面分析

| 涉及项 | 类型（模块/文件/接口） | 影响说明 |
|--------|------------------------|----------|
| 数据根与注册表 | `runtime/core/data-root.cjs`、`service-registry.cjs` | 默认路径、旧路径兼容和系统索引位置变化 |
| 项目私有数据 | `runtime/desktop-client.cjs`、`snapshot.cjs` | 凭据允许进入受保护项目目录，运行目录从候选快照排除 |
| 管理台改绑 | `runtime/admin.cjs`、`runtime/web/`、邀请与交接模块 | 新增一次性邀请创建、领取、取消和状态展示 |
| 审核完整性 | `dispatcher.cjs`、`scope-recovery.cjs` | 将控制面漂移与业务候选漂移分离 |
| 兼容与迁移 | 启动器、测试、运行文档 | 旧显式 `--data` 与旧凭据继续可用，迁移需停止服务并校验 |

## 3. 边界与异常场景

| 场景 | 预期行为 |
|------|----------|
| 无 workspace 打开管理入口 | 不创建或启动空公共服务；提示选择 workspace 或从索引选择项目 |
| 项目路径含中文、空格或同名目录 | 使用规范化 workspaceKey 隔离，路径稳定且不碰撞 |
| `.task-dispatch/runtime/` 被 Git 扫描 | 自动生成局部 `.gitignore`，快照强制排除运行目录 |
| 改绑邀请重复领取、过期或状态已变化 | 幂等返回已完成结果，或明确拒绝并保留当前绑定 |
| 旧端仍有在途任务 | 普通角色进入安全 handover；明确恢复的 brain 可转移合法所有权 |
| 改绑成功后旧端提交 | 旧 token 已撤销，提交被拒绝 |
| 候选后仅计划文件变化 | 记录控制面漂移事件并继续原候选审核 |
| 候选后业务文件变化 | 保持 stale candidate 阻塞，不自动覆盖或放宽权限 |
| 旧旁挂目录迁移中失败 | 索引不切换，旧目录保留，可重新执行 |

## 4. 技术方案

- **选定方案**：严格项目内方案。项目状态、快照、收据、审核副本、连接描述、凭据均进入 `.task-dispatch/runtime/<project-key>/`；系统缓存仅保存服务注册表。
- **被否决方案**：旁挂项目目录会造成路径割裂；用户级公共服务会产生空实例；系统级凭据库不满足用户“凭据严格项目内”的确认。

### 关键设计

- `projectDataRoot(workspace)` 返回 `<workspace>/.task-dispatch/runtime/<workspaceKey>`。
- 项目内 `.task-dispatch/.gitignore` 忽略 `runtime/`，运行目录以 0700 创建，敏感文件由原子写入使用 0600。
- 快照默认排除 `.task-dispatch/runtime/`，但仍纳入 `.task-dispatch/plan.md`，确保 worker 越权修改计划可以被检测。
- 系统注册表放入平台缓存目录的 `task-dispatch/service-registry.json`，只记录绝对工作区和数据根，不记录 token。
- 改绑邀请使用随机 ID、过期时间、目标 binding、旧 clientId 和状态；提示词不含 token，新会话通过 invitation ID 生成自己的 token 并领取。
- 服务端绑定替换复用 handover/recovery 保护，邀请状态与绑定变更由同一持久化状态提交完成。
- 审核前后比较候选与实时 manifest 的文件差异；只允许 `scope-recovery` 已定义的 authority/control 文件漂移，业务文件差异仍失败。

## 5. 实现流程

```text
connect(workspace)
  → 解析 workspace/.task-dispatch/runtime/<key>
  → 确保私有目录与局部 ignore
  → 启动/复用该项目唯一服务
  → 凭据写入项目运行目录

管理台 rebind
  → 创建一次性邀请
  → 新会话 rebind --invitation-id
  → 校验项目、角色、旧绑定和过期时间
  → handover/recover
  → 撤销旧 token、完成邀请并刷新 UI

审核候选
  → manifest diff
  → 仅控制面文件：审计并继续
  → 含业务文件：阻塞并要求协调
```

1. 修改数据根、注册表与入口解析，保留显式 `--data` 和旧凭据兼容。
2. 增加项目内目录保护与快照排除。
3. 增加一次性改绑邀请的服务状态、管理命令、CLI 领取和 Web UI。
4. 增加控制面漂移分类与续审逻辑。
5. 增加迁移预检/执行能力、回归测试和运行文档。

## 6. 验证方式

- **用户提供的验证方法**：复核最近一次 mimotest 试跑；缓存应位于项目内，且更新 `.task-dispatch/plan.md` 后 T03 审核不再误阻塞。
- **构建验证**：项目根目录执行 `npm test` 与 `node scripts/verify.js`。
- **验证结论**：项目全量自动化测试通过；安装器验证通过；定向覆盖项目内凭据、迁移源保留、改绑幂等/取消/所有权转移、控制面漂移续审与业务漂移阻塞。
