# 系统索引布局 — 技术方案

## 需求概述

用户主目录保留轻量系统总目录与每项目元数据子目录；项目工作目录承载各自服务状态、凭据、快照和 diff。兼容现有 AppData 索引。

## 影响面与边界

- 系统目录：`~/.task-dispatch-service/service-registry.json`、`console.json`、`projects/<项目键>/project.json`。
- 项目缓存：`<workspace>/.task-dispatch/runtime/<项目键>/`。
- 旧 AppData 索引仅作为首次导入和控制台复用兼容源；不移动业务快照。
- 索引缺失或损坏时，仍可从有效项目服务状态恢复目录；显式测试文件路径不受默认路径改变影响。

## 技术方案

采用用户指定的分层目录。目录注册时若新索引不存在，合并旧 AppData 与旧用户目录索引，再写新注册表和每项目描述文件。控制台优先读取新运行记录，兼容旧运行记录。用户目录被保留作索引时，新的连接不能把它当作快照服务目录；旧系统目录若仍含既有服务数据，保持兼容读取。

## 实现流程

1. `connect` 由工作目录计算项目缓存路径并启动项目服务。
2. 项目服务登记时更新用户总目录注册表和对应项目元数据目录。
3. 管理台从系统索引找到项目服务；服务的大文件始终留在项目工作目录。

## 验证方式

用户未提供新验证步骤；`npm test` 261/261 通过。真实服务重启后，用户总目录含注册表、控制台状态和两个项目元数据目录；HYAlgLib 的项目服务仍位于其工作目录，控制台 HTTP 200。旧 AppData 两个文件的删除被自动审批策略拒绝，原样保留；新代码不再向该目录写默认索引。

## 遗留问题

已导入的旧 AppData `console.json` 和 `service-registry.json` 仅作兼容遗留，当前运行的控制台使用用户总目录。宿主平台自身 API 响应或模型启动耗时仍取决于对应应用；本次减少了客户端重复核实和 MiMo 连接时的事件等待。
