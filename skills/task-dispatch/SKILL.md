# Task Dispatch

## 目标授权与启动

Web 创建目标返回 `peerSetupManagedBy: web`、`goals`、`activeGoalId` 与 `brief`。默认“大脑＋初审端＋一名执行员”，各端可同时 connect，大脑复用配置及绑定，不重复 staff、邀请或派生。用户点击「创建并开始」已明确授权，服务在全员就绪且轮到目标时投递 planning，不再要求重复开始；「仅保存」必须等用户明确开始才入队。同目录持续新增目标，逐个完成，活动期间不修改团队。用户已明确指定接收端平台时沿用，不重复询问。详见 [服务发现与接入](references/connection.md)。

目标项目按 planning.goalId/brief 处理当前目标，任务与阶段自动关联当前 goalId，编号在项目内唯一。完成当前目标全部验收并通过阶段终审与结算后，实际执行 `finish-goal --goal <goalId> --summary <验收摘要>`，随后 `resume`；服务处理下个已授权目标，队列为空则待命。阻塞时保留当前目标并报告具体原因；不得用 finish-project 跳过目标。已有单目标契约和历史不改写，换会话仍显式改绑。

非 Web 目标项目采用两阶段启动：连接阶段只登记 staffing、生成邀请、核对各端，不得 plan。计划内 worker 与小脑就绪后，等待用户在大脑会话明确发出开始指令，再执行 start-work --confirmed，成功后才 plan。connect 成功配置唤醒后自动 park，返回 parked:true 即待命，其他角色无需用户再次确认；大脑派单后同样实际 resume；无唤醒端接入后实际 wait --seconds 60 保持可领取，宿主工具超时至少 90 秒，不把空队列当完成。小脑必须就绪，不支持跳过初审。后续已授权任务、审核、返修与唤醒自动继续，不逐单要求人工确认。已结束项目重新打开后重新等待开始；服务重启或普通重连不重置已启动项目。服务只能校验大脑提交的明确确认，不能独立识别聊天中是否为真人发令，大脑不得自行代替用户确认。

```powershell
node "<客户端脚本>" start-work --confirmed --credential "<大脑凭据>" --data "<服务目录>"
```

status.startup.state 为 waiting 时不得派单；started 表示已启动。

以完成并验证功能的总成本为目标，同时考虑模型调用、交接、返工和人工时间。不要承诺固定节省比例，也不要按任务数量规定模型使用比例。

## 范围与运行方式

- 保留用户当前目标及授权：只要求计划时生成计划；要求开发时推进实现；要求审核时检查成果。使用此技能不会自动授权发布、付费调用或跨平台传输代码。
- 强模型和经济模型是角色，不是写死的厂商或型号。优先采用用户指定的映射；未指定时可先输出角色化任务包。仅在确有选择需要时核实可用模型和计费方式。
- 此技能提供流程，不提供模型路由器。若已有可调用且获授权的执行工具，可按其能力分派；遵守宿主对子代理和模型覆盖的限制，不因技能加载而自行启动代理。只有用户明确要求新建可见任务时才创建此类任务。
- 大脑只负责分析、规划、拆分、派发和审核，不实现业务代码。没有匹配执行员时输出对应邀请并等待，不自行接手、不静默降级强模型任务。所有实现交给 worker；大脑可维护计划和审核记录。
- 小任务不需要为节省成本额外安排一次规划和审核。复杂项目先做能跑通的最小功能闭环，接口稳定后再批量下放。

## 拆分与审核决策

先读取项目现有规则、有关代码和现有检查命令。建立最小依赖关系，只为近期可执行工作细化任务。每个任务应有明确目标、修改边界和可观察的验收条件。

| 条件 | 执行与审核策略 |
| --- | --- |
| 共享接口、存档格式、核心状态规则或多个任务依赖的基础实现 | 大脑明确共享契约，强模型 worker 完整实现；必要时大脑提前确认契约，正常依赖由小脑初审通过释放 |
| 支付、权限、数据迁移、联机一致性或跨模块疑难问题 | 强模型 worker 负责关键实现，大脑在阶段终审独立审核；重大契约冲突提前上报 |
| 边界清楚、可独立回滚、沿用已有模式的功能 | 经济模型执行，相关检查通过后可继续独立任务，完整功能阶段集中终审 |
| 机械修改、文案或已有可靠自动检查的局部变更 | worker 实现并执行适用检查，小脑初审，大脑在所属完整功能阶段终审 |

拆分依据是可独立交付和验收的边界，不为适配经济模型或凑任务尝试次数拆碎紧密耦合的任务。复杂且边界明确的任务完整交强模型 worker，内部自行分步骤实现。

不要机械套用“每批 3～8 个任务”或“涉及三个模块必定升级”。按耦合、变更规模、可验证性决定批次。一项任务若包含独立 UI 与高风险持久化逻辑，应拆开判定。

小脑初审通过释放同一阶段内的普通依赖，但不标记 accepted。大脑事先制定完整阶段计划，覆盖该功能及相关修复任务；全部初审通过后统一终审。跨阶段依赖必须等待前一阶段最终通过。获授权的并行执行应分离修改文件或使用独立工作区，明确集成人员。

## 阶段集中终审（唯一工作流）

以一个完整功能阶段及相关修复为计划单位。大脑明确目标、完整任务清单、契约、依赖和验收条件；`plan` 只登记草案，全部任务登记完后必须 `stage-register` 提交完整计划才派发。一个阶段可以只有一个任务，也允许依赖和顺序修改相同文件。

小脑只审核既定任务，可以要求按原任务返修，不得新增、删除、修改任务或降低验收条件。契约冲突、计划缺漏、阻塞、连续修复无进展应提前上报大脑。大脑阶段终审同时检查原始需求、整体功能、接口衔接和回归；不能只确认小脑结论。

终审失败时，大脑读取问题清单，追加新的修复任务，使用相同 stageId 和新 roundId，逐项关联 repairKeys；全部修复任务初审通过后，再对整个阶段累计成果终审。直到整体验收通过，才推进下一完整功能阶段或结束项目。操作、回执和异常恢复见 [阶段计划与终审](references/stages.md)。不支持逐项终审、可选批量开关、无小脑启动或旧队列迁移。

## 执行与交接

worker 在大脑明确的目标、共享契约、允许路径和验收条件内自主选择实现细节并完成整个交付；不得自行改变共享契约或扩展任务。仅在缺失前提、契约冲突或需要扩大范围时，以 blocked 回执报告具体证据，不因普通实现选择或内部步骤较多而阻塞。docs/plans/ 和 docs/reviews/ 全目录仅大脑可写，allowedPaths 中列出也不能授权 worker 修改。业务代码仍以 allowedPaths 为边界；需要文件形式的执行回执、测试结果或日志时，仅写明确列入 allowedPaths 的 docs/worker-results/<当前任务ID>/ 路径。最终 JSON 回执仍按服务协议提交，不修改任务状态。 计划、契约和任务定义放 docs/plans/，审核结论放 docs/reviews/。大脑一次审核实现与执行证据，不为回执文档另开设计审核；服务负责路径、回执格式和已配置检查等机械验证。目标、共享接口和验收边界在派发前由大脑明确；边界内的算法、内部结构及实现顺序由 worker 决定，强模型任务不要求拆成逐行操作。

收到 scopeRecovery 时，先重读项目规则，对照原始快照、被拒候选和当前差异，仅纠正本人造成的越界内容，保留业务实现与他人改动，不重做任务、不扩大允许路径。仅允许恢复到服务列出的 expected 校验值；无法区分修改来源就返回 blocked。两轮纠正仍失败则交由大脑处理。

worker 的 blocked 回执和一切 blocked/uncertain 结算都会由服务登记 task_attention 并自动唤醒大脑，与 scope_attention 走同一通道；无匹配执行员保持 ready 除外。大脑被唤醒后先核对阻塞原因，再选择 retry/assign --retry、task-budget、在允许边界内调整计划或向用户求助，处置完成后执行 attention-ack 确认通知；确认本身不放行任务。等待型（无唤醒）执行端不主动探测会话存活：管理台以请求静默时长提示 wait_stalled 与 connection_silent，需要人工回原会话核实。

大脑是已授权工作流的控制面最高处置者：可用自身凭据执行 retry、assign、task-budget、configure-repair、reconcile-review、revise-task，并可登记带 `supersedes` 的替代任务或在替代任务已 accepted 后执行 resolve-task。阶段登记后不可追加成员或改变已执行契约；configure-repair、reconcile-review 和替代任务不能绕过阶段冻结。上述权限不能绕过用户对真实外部调用、费用、发布或范围扩张的授权，也不能直接把未审核实现改成 accepted，不能在未确认旧进程停止时清除 uncertain。

计划与任务契约分层管理：大脑可随时更新 `docs/plans/` 与 `.task-dispatch/plan.md`，这些控制面变化记录为 controlDrift，不应让业务候选 stale；尚未产生 attempt 的 ready 任务在项目暂停且阶段空闲时可用 revise-task 显式修订并递增 contractRevision。任务一旦产生 attempt，其 instructions、acceptance、allowedPaths 和 dependsOn 即冻结；阶段内需要改变已执行契约时，先上报大脑明确处理；若必须重新规划，需核实执行已停止，通过管理台整体重置阶段，保留重置审计，再登记新计划。阶段外替代旧 blocked 任务可创建新 ID，并用 `supersedes` + `supersedeReason` 明确关联。替代任务 accepted 后旧任务进入 resolved（管理端显示“已由后续任务解决”），保留原失败与替代证据，不伪装成 accepted。

首次生成任务单或审核结果时，读取 [任务与验收模板](references/handoff.md)，只填对当前工作有用的字段。

- 交付目标、接口约定、必要代码位置、依赖、禁止改动项及验收方式；不要复制整段对话或整个代码库。
- 实施型多阶段任务可将记录保存在项目现有任务目录；无既有目录时使用项目内 `.task-dispatch/`。建议 `plan.md` 保存任务状态和审核点，`tasks/<id>.md` 保存有实际交接需要的任务。讨论或一次性小任务不强制写文件。
- 执行者报告修改文件、变更摘要、实际运行的命令与结果、未解决问题；在 Git 项目中提供提交或明确 Diff 范围。成功陈述不能代替检查证据。
- 每项任务只运行相关检查。小型改动无需每次全量构建；在集成阶段执行适当构建和回归。不存在的测试标记为未验证，不编造通过结果。
- 游戏功能除编译外，按需求检查场景引用、资源绑定和运行行为；手感、画面和乐趣不能仅凭单元测试判定。应用功能按需求检查交互、错误状态和持久化行为。
- 经济模型连续两轮针对同一问题的修复仍无进展时，默认交回强模型诊断；发现接口冲突、范围扩张或关键需求不清时更早升级。升级包仅包含复现、错误输出、相关 Diff 和已尝试方案。

## 任务尝试次数与执行者

每个任务独立使用尝试额度（runtime 默认 maxAttempts: 30），新任务从 0 开始；新执行 attempt 与新审核 attempt 各计一次，重复领取、内部工具调用、规划和交接等待不计数。返修、重试、恢复、换绑及升级模型不清零，项目累计次数持续保留。项目累计保护可选，不能默认用固定项目上限阻断后续任务。

计划执行者 plannedWorkerId 与当前执行者 currentWorkerId 分开保存。升级只调整当前任务，后续返修沿用升级后的 worker；新任务读取自己的计划分配。跨任务延续强模型必须由大脑明确调整对应未开始任务并记录原因（assign --update-plan --reason）。升级不追加额度；确有需要时独立调用 task-budget --task <任务ID> --add <追加次数> --reason "原因"。仍按计划分配强模型和经济模型，不增加自动模型选型策略。操作见 [多执行员接入](references/workers.md)。

## 审核与收尾

### 可选本地 runtime

用户要求派发、新增执行端、断绑或换绑时，读取 [多执行员接入](references/workers.md)。Web 目标沿用页面的开始授权及团队；其他项目先完成各端接入，用户在大脑会话说一次开始，由大脑核对就绪后 start-work，再派单；支持 wake 的平台实际 wake-bind/park，无唤醒平台任务提交后实际 wait，不能仅回复等待就结束。其他连接阶段按 [服务发现与接入](references/connection.md) 派生一个独立小脑 reviewer：所有阶段成员先逐项初审，全部通过后大脑对整合成果集中终审；未连接 reviewer 则阶段阻塞，不降级逐项大脑审核。已领取初审不以 heartbeat 续约，也不因暂态读取失败自动改派；确定停止时 reviewer 自己 detach，崩溃时由 brain 明确执行 `detach --role reviewer`。该操作撤销旧 reviewer 绑定并等待新 reviewer 恢复初审，绝不能根据超时擅自执行。派生需要宿主支持和已有用户授权，不得假装已连接。非 Web 管理项目的 brain connect 后先评估本阶段所需模型类型、数量、职责及并发条件，复用现有合适 worker，再以 staff --file 登记并展示逐编号邀请；模型不会自行创建或假装关联另一个窗口。按任务的强模型等约束填写 workerId/requiredCapability，未匹配时明确等待接入。

用户要求通过服务协作、派发任务或继续开发时，先读取 [服务发现与接入](references/connection.md)，默认当前会话为 brain、当前工作目录为项目，调用 connect 自动启动服务并创建或复用绑定，不要求用户提供可自动确定的目录或凭据。用户已指定 worker 身份时保留 worker，不切换角色。只规划时不接入、不提交。用户明确要求继续派发或开发时使用 connect --continue 重新打开已结束的同目录项目，不另造同目录项目。接入服务后以服务状态为唯一任务进度来源，本地计划只记录设计和说明，不能据聊天记录自行判定任务已通过。

用户要求“当前窗口接入”“你是审核员/执行员”“阻塞等待另一端”时，先读取 [桌面会话接入](references/desktop.md)，使用 desktop-client 的 attach/wait/plan/submit 流程。该模式不需要配置平台 App Server，等待由本地脚本承担；遵守宿主的工具执行时长和进程续等规则，不宣称已经验证所有 Desktop 的无限等待。

Qoder/QoderCN 属于原会话唤醒平台：先 `node scripts/install.js qoder`（或 `qodercn`）安装技能、首次握手 Hook 与常驻 App Plugin 直接唤醒桥接，并重启 Qoder 一次。connect/rebind 必须显式传 `--provider qoder`；首次连接优先传邀请自带的 `--invitation-id`，也可传宿主真实 `--session-id`。成功返回 `parked:true` 即长期待命，不依赖 Stop Hook 轮询或监听租约；若返回 job 则立即处理。Qoder 不能静默降级为 wait。细节见 [Qoder 原会话接入](references/qoder.md)。

OpenCode 2.x 支持 brain、reviewer 和 worker 原会话唤醒。接收端确认平台后，使用真实 `ses_...` 会话 ID；需要 Node.js 22.13+、可读会话数据库和官方 CLI。安装及接入时读取 [OpenCode 原会话接入](references/opencode.md)。

若用户已配置 task-dispatch 本地服务，规划者将任务包映射为 `id/title/instructions/acceptance/allowedPaths/dependsOn`，通过已授权的管理端登记。替代旧阻塞任务时额外填写 `supersedes`（旧任务 ID 数组）与 `supersedeReason`；不得按任务名猜测替代关系。先添加前置任务；`allowedPaths` 使用相对文件名或以 `/` 结尾的目录，不使用通配符。服务代码在开发仓库 `runtime/`，配置与恢复说明在 `docs/runtime.md`；这些不随 Skill 复制安装，不能假定本机已存在或已启动。

作为服务派发的执行员或审核员时，遵守宿主提供的项目、任务、尝试及角色绑定，最终返回宿主要求的 JSON。执行员不得自审通过；审核员不得修改候选。不得直接修改服务状态、调用管理接口替自己放行或另起后台代理。遇到中断不猜测完成，交给服务按回执恢复。普通手动交接仍沿用本 Skill 模板，不强制使用 runtime。

强模型根据验收条件查看实际 Diff、相关上下文和检查证据。重点看需求符合性、接口一致性、回归和集成问题，不强制重写风格。

审核结果使用“通过 / 需修复 / 阻塞”，问题需有文件位置、触发条件、影响和必要修复。任务初审通过后保持 `review_ready` 并标记 `stageHeld`；阶段整体终审通过才将累计任务变为 `accepted`。小脑 needs_fix 按原契约返修；大脑终审 needs_fix 后由大脑追加新任务并关联问题，原任务不重开。状态主链为 `ready → running → review_ready → reviewing → review_ready（初审通过） → accepted（阶段通过）`；失败或缺失前提进入 `blocked/uncertain`。旧阻塞被一个显式关联且已 accepted 的替代任务解决后进入 `resolved`，它是终态但不等于原任务通过。修改后的内容需重新验证，旧审核不覆盖新 Diff。

只把已满足验收条件的工作标记完成。最终报告交付内容、实际验证、待审核或未验证项。跨会话继续时读取已保存状态和当前代码，避免重新规划或重复实现已完成工作。


### 客户端自动选择续接方式

当前客户端 connect/rebind 要求接收端显式传 `--provider <真实平台>`。每个 brain、reviewer、worker 接收端在首次连接或换绑前都必须先询问用户当前会话平台，由用户明确选择；不得根据模型、目录、环境变量或邀请来源猜测。用户未选择时停止连接，CLI 也会硬阻断缺失或 `auto` provider。brain/reviewer 可使用 codex、mimo、qoder、opencode；worker 可用合法 provider。codex、mimo、codearts、opencode 走 wake 并要求真实 session；qoder 首次连接可用当前邀请的一次性 ID 核实真实 session；其他 worker provider 快速进入 wait。brain connect 返回 `setup-peers` 时必须展示 reviewer 邀请；完成 staff 后逐条展示 worker 邀请，不能只回复等待。首次 resume 配置也必须显式 provider；已有 wake/continuation 才可省略并复用。具体见 references/desktop.md。

brain 正常换绑使用 `rebind --role brain`。旧 brain 已永久不可用时，只有用户明确确认旧会话及后台任务均停止后，才可追加 `--recover --confirmed-stopped`；禁止模型自行确认。确认式恢复撤销旧凭据、替换遗留 pending handover，并把未结算 brain attempt 原样转交新 brain。worker/reviewer 不支持该参数，继续使用保守交接。
