# 任务与验收模板

模板用于模型之间或人工复制交接，按需省略字段。占位文本必须替换为真实内容；不要为了填满模板臆造命令或约束。

## 阶段计划

```markdown
# 本阶段目标
目标及完成标准：
角色映射：设计/审核模型；执行模型；实际调用方式（工具或手动）
公共约定：接口、数据结构、项目规则位置

| ID | 交付物 | 依赖 | 执行角色 | 审核时机 | 状态 |
| --- | --- | --- | --- | --- | --- |

本次可执行：
待审且阻塞下游：
集成时运行的检查：
下一步：
```

## 执行任务包

```markdown
# T-ID：任务名
目标：可观察的行为变化
依赖：前置任务及必须通过的审核
输入：必要代码路径、接口定义、参考实现
允许修改：业务文件或模块边界；可选执行证据仅列 docs/worker-results/T-ID/
只读输入：docs/plans/ 的已定计划、契约及任务定义；docs/reviews/ 的审核结论
约束：需保持的契约及不得改动的内容
验收：正常行为、相关边界条件、适用的检查命令或手动步骤
审核：立即审核 / 里程碑批量审核 / 自动检查后接受，并说明原因

执行说明：
仅按大脑已定步骤与契约实现。需要选择方案、契约缺失或约定与代码冲突时返回 blocked 并报告证据，
不自行扩展为跨模块重构。完成后提供变更摘要、实际检查结果和遗留问题。
```

## 执行结果与审核包

```markdown
任务与实际执行者：
状态：
修改文件和 Diff 范围（有提交时附基准与结果提交）：
行为变化：
检查：命令/步骤 → 实际结果
未验证项及原因：
问题与已尝试修复（失败时填写）：
阻塞所缺前提（无则省略）：
```

审核者补充：`通过 / 需修复 / 阻塞`、问题证据、释放的依赖任务。无 Git 时以明确文件范围及当前文件内容为依据，不编造提交 ID。

## 游戏开发示例

背包数据模型 T1 影响 UI T2 和存档 T3：先审核 T1 的物品 ID、堆叠与数量规则，再释放 T2/T3。存档兼容性单独重点审核。制作人员页面 T4 与上述工作独立，T1 待审时仍可执行 T4。

音量滑块若依赖已有稳定设置接口，可由经济模型直接实施，检查即时生效与重启后恢复，再并入设置模块审核。若需要引入新的存档机制，应拆出该基础任务并先审核。
